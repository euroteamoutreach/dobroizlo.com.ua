1 · What We Did (and Why It Matters)

The marketing site went live on 2026-06-22, but its repo was stuck in a temporary "private bridge" on a personal account (joshukraine/dobroizlo.com.ua). It couldn't simply be flipped public because licensed Tailwind Plus snippets, committed early in development, survived a history rewrite as dangling-but-still-fetchable commits. This work resolved that and landed the repo at its intended home.

The end state — and the close-out of ROADMAP Phase 10 (now fully Complete) — is the repo living at euroteamoutreach/dobroizlo.com.ua: public, org-owned, deploying free on Netlify, with no trace of the licensed content anywhere in code, history, or by raw SHA.

2 · Key Decisions & Tradeoffs

The core insight: a fresh repo carries only reachable objects

A history rewrite (git-filter-repo) had already removed docs/tailwind_plus/ from every reachable commit on main. But three pre-rewrite commits (984e892, 4762dc1, 4b8adda) lingered as dangling objects that GitHub still served by raw SHA. Force-push and branch deletion don't reap those.

The decision was to rebuild rather than scrub. git push only transmits objects reachable from the pushed ref, and a fresh git clone never even fetches dangling objects — so pushing a fresh clone's main into an empty repo cannot carry the bad commits. No GC, no support ticket, no risk.

Rejected alternatives

OptionWhy rejected
GitHub Support GC requestGitHub's policy only removes rotatable-credential sensitive data, not licensed code in a never-public repo — would very likely be declined.
Transfer private repo to org as-is + Netlify ProPrivate org-owned repos cost ~$240/yr to deploy on Netlify, and it would carry the dangling commits along.
Just force-push + delete branchesAlready done previously — doesn't reap dangling objects; they stayed fetchable by SHA.

Zero-downtime relink

The Netlify site (dobro-i-zlo) was never recreated — only the Git repo it builds from changed. Domain, DNS records, the Let's Encrypt cert, env vars, redirects, and headers all travel with the site, not the repo. Netlify only swaps in a new deploy after it builds green, so the previously published build served traffic the entire time. No DNS edits were needed (which also kept us clear of the "never touch DNS without approval" rule).

Branch protection: required the right checks

The instinct was to "require the Netlify deploy check." But on direct main commits, no Netlify check fires — its deploy-preview status only posts on PRs. Requiring a context that never reports would have silently frozen all merges to a live site. Instead we required the two GitHub Actions checks that run on both push and PR: Hugo Build (the canonical hugo --gc --minify verification) and Markdown Lint.

enforce_admins is deliberately false — the owner can still hotfix-push to main in a pinch (demonstrated when the one-line version reconcile was pushed and GitHub reported "Bypassed rule violations"). Force-push and deletion are blocked for everyone.

Replace, don't deprecate The fresh repo shipped with GitHub's 9 default labels (bug, enhancement, …). Rather than layer the project's feat/fix/chore/docs/test taxonomy on top, we deleted the redundant defaults so the label set is unambiguous — one vocabulary, not two overlapping ones.
